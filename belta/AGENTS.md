# AGENTS.md

## Development Rules

- This project is in active rewrite/development. Do not preserve compatibility with old commands, old file layouts, or previous scaffolding unless explicitly requested.
- When the design changes, update implementation and tests to the latest `DESIGN.md` behavior and delete obsolete legacy code paths, test expectations, generated-output schemas, and compatibility branches instead of keeping parallel old/new behavior.
- Keep one canonical current version of active configs, exported tasks, and Harbor results. When their contents change, regenerate or overwrite the current outputs instead of retaining parallel legacy variants. Do not add schema-version branches or migrations solely to preserve old generated outputs. Content checksums are only guards for detecting stale results; they do not require preserving older task versions.
- Implement from `DESIGN.md` as the intended final behavior, not as a temporary prototype. Prefer the most reasonable, stable, and standard engineering approach for the documented workflow; do not add ad hoc shortcuts for local network/debugging issues unless the design explicitly adopts them.
- Integrate FeatureFactory as a runnable library/module, following the Repository Discovery pattern: import FeatureFactory from the configured `featurefactory.root`, initialize its settings/database/runtime through its public service/runner APIs, and run or reuse the corresponding FF stage as part of Belta. Do not implement Belta as a scraper that only scans pre-existing FF artifact folders or manually copies local outputs; local artifacts are validation/debug evidence, not the primary integration contract.
- Belta owns its runtime configuration. Load Belta's own `.env` and YAML config only; do not implicitly load the FeatureFactory checkout's project-local `.env`. Any FeatureFactory setting required by Belta's FF integration must be declared on the Belta side and passed into FF settings explicitly.
- Prefer one current command or interface over aliases. If a name changes during design, update the implementation to the new name and remove the old one.
- Keep implementation aligned with `DESIGN.md`. Do not add extra phases, outputs, logs, compatibility paths, or abstractions before the design calls for them.
- Do not add speculative schema versions, provenance fields, defensive validations, status codes, diagnostics, or metadata solely for hypothetical misuse. Add them only when the current documented workflow requires them or a reproducible observed failure demonstrates that they are necessary. If an existing workflow invariant already guarantees a condition, rely on that invariant instead of adding redundant checks or outputs.
- Keep naming consistent across `PROJECT.md`, `DESIGN.md`, implementation, configs, and generated artifact names. If a concept is renamed, update all references in the same change.
- Use the current benchmark terminology from the docs. Candidate Pair Construction uses `reinsert_targets` and `implementation_units`; Retire Task Construction uses `gold_cleanup.patch` as the oracle/reference cleanup patch. Treat `reinsert_targets.jsonl` as private audit material, not the final scoring oracle. Do not call candidate-stage targets `gold`, and do not use older names such as `removal_targets`, `deleted_objects`, or earlier gold-target names.
- Candidate Pair Construction records only `implementation_code_paths`; do not reintroduce the obsolete `path_classes`, `test_related`, `environment`, or `excluded` candidate-output schema. FF Stage2 owns test discovery and the later `validation_test_universe`.
- Treat the bare repo cache as a cross-run Git object store. The first Candidate Pair Construction attempt for a repo in each new run validates the cache and incrementally fetches the remote default branch; a failed fetch must fail that repo instead of silently using a stale ref. Within the same run, reuse the commit SHA already recorded for a completed repo. Clone only when the cache is missing or invalid.
- Do not materialize `old_to_new.patch` as a standard pair or task artifact. The full diff is derivable on demand from `old_commit`, `new_commit`, and the bare repo cache; retain only task-relevant implementation and reinsert materials.
- When adding or changing config fields, also update the local example configs under `configs/` so the current runnable shape is easy to inspect and debug.
- Local configs and generated data may contain debugging secrets and must stay ignored by Git.
